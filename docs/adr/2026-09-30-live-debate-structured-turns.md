# ADR-094: 4人のAIの各発言に、画面用の要約・誰への返事か・根拠を付けて返させる

## 日付

2026-09-30

## 状況

解析結果の画面の待ち時間に、4人のAIの議論を1発言ずつ見せる（#194）。LIVE-1（#195、ADR-085）で議論の材料を増やした。次は、画面に出す文を作る（#196）。

- アナリスト・イノベーター・スケプティックは自由な文章で返していた（`DebateAdviceGeneratorService.singleChat`）。その文章が、そのまま次の発言者とディレクターに渡る
- 自由文は画面に出すには長く、「AI可視性ランク」などの用語や、イノベーターの `[引用: …]` の形も混ざる
- 3人のモデルのビーン（`AiConfig.GEMINI_DEBATE_ANALYST` ほか）とシステムプロンプト（`DebatePersonaSystemPrompts.forPersona`）は、オンボーディングの議論（`DebateOnboardingOrchestrator`）と共用している
- ディレクターは総合診断・ロードマップ・少数意見を JSON で返すだけで、発言にあたる文を持っていない。見本の画面（#199）には、最後にディレクターの「まとめます。…」という発言がある

## 決定

### 1. 3人の出力を構造化する

新しい `DebateTurnOutputSchema` で、1発言を次の JSON で返させる。

| 項目 | 中身 |
|---|---|
| `discussion` | 議論用の本文（今までの自由文に当たる） |
| `screen_summary` | 画面用の要約。2〜3文・120文字以内 |
| `reply_to` | 誰への返事か（`NONE`・`ANALYST`・`INNOVATOR`・`SKEPTIC`） |
| `stance` | 返事の立場（`NONE`・反論・賛成・条件つきで賛成・確認・応答） |
| `evidence_kind` | 根拠の種類（`NONE`・質問ごとの言及・回答によく出た他社・サイト診断・改善タスク） |
| `evidence_task_number` | 根拠が改善タスクのときの番号 |
| `evidence_detail` | 根拠の中身（60文字以内） |

- 立場は issue の4つに、見本の画面の「スケプティックへの応答」（指摘を受けて案を直す発言）に当たる「応答」を足した
- 根拠は1発言に1つ。種類は、議論の材料の節（ADR-085）と改善タスクに対応させた。依頼時の事業の前提は、測定の結果ではないので根拠に含めない
- 列挙には「無し」（`NONE`）を持たせ、項目はすべて必須にした。null を返させるより形が崩れにくいため
- `discussion` を先頭に置いた。Gemini は並び順に書くので、本文を書き終えてから要約させるため

### 2. 書式はビーンではなく、呼び出しごとに渡す

- 出力の形は `ChatRequest.responseFormat` で呼び出しごとに渡す。LangChain4j 0.36.2 の `GoogleAiGeminiChatModel.chat(ChatRequest)` は、呼び出しの書式があればそれを、無ければビーンの書式を使う（バイトコードで確かめた）。3人のビーンは書式を持たないので、オンボーディングの議論は自由文のまま変わらない
- 画面用の書き方の指示は、共用のシステムプロンプトの後ろに、この呼び出しでだけ足す（`screenOutputRules`）。共用のシステムプロンプトは GEO の用語を使うよう指示しているため、要約では「GEO」「AI可視性ランク」などの用語も使わないよう上書きする

### 3. 次の発言者とディレクターには、今どおり議論用の本文を渡す

画面用の要約は画面にだけ使う。議論の質を落とさないため、次の発言者とディレクターへの入力は、今までの自由文に当たる `discussion` だけにした。

### 4. 壊れた出力を直す。議論は止めない

| 壊れ方 | 扱い |
|---|---|
| JSON として読めない | 応答の全文を本文として次へ渡す。要約は空、返事・根拠は無し |
| 本文が空 | 要約を本文として次へ渡す |
| 要約が長すぎる | 120文字以内で最後の「。」まで残す。「。」が無ければ119文字で切って「…」を付ける。改行は消す |
| 要約が空 | 空のまま持つ。画面でどう見せるかは LIVE-5（#199）で決める |
| 返事の相手が、その発言者の読んでいない人・自分自身 | 返事なし（立場も無し）にする |
| 根拠の改善タスクの番号が存在しない | 根拠を捨てる |
| 測定結果の根拠で中身が空 | 根拠を捨てる |

発言者が読める相手は、アナリストとイノベーターが「前のラウンドまでの3人」、スケプティックが「同じラウンドのアナリストとイノベーター」。1ラウンド目のアナリストとイノベーターは、まだ誰の発言も読んでいない。モデルの呼び出し自体が失敗したときは、今までどおり議論全体を失敗として扱う（チケットを返して単発生成に戻る）。

### 5. ディレクターに、画面用のまとめの一言を書かせる（2026-09-30 オーナー）

ディレクターの出力（`DebateAdviceOutputSchema`）に `debate_summary` を足した。議論で決まった進め方と、少数意見として残した案を、2〜3文・120文字以内で書かせる。議論が無い回は空文字を返させる（スキーマは静的なので必須のまま）。

候補は「AIに書かせる」「画面でロードマップの件数から組み立てる」「まとめの発言は出さない」の3つで、オーナーは「AIに書かせる」を選んだ。追加の呼び出しは無く、出力が百数十文字増えるだけで済む。

### 6. 画面用の発言は `JobAdvice.utterances` で返す

新しい `DebateUtterance`（ラウンド・発言者・要約・誰への返事か・立場・根拠）を、話した順に `DebateAdviceGeneratorService.JobAdvice` に載せる。3人×2ラウンドの6件のあとに、ディレクターの1件（ラウンドは無し）が続く。議論が走らなかった回・失敗した回は空。

今回は返すだけで、保存（LIVE-3 #197）と画面（LIVE-4〜6）はまだ使わない。`JobAdvice` には従来の3引数の形も残し、呼び出し元（`StrategyInsightService`）は変えていない。

## 理由

- **同じ呼び出しで要約させる理由**: 要約だけ別の呼び出しにすると、呼び出しが6回増える。発言者が自分の本文を要約するので、立場の食い違いも起きない
- **要約が空でも発言を残す理由**: 発言を消すと「イノベーターへの反論」のような返事の相手が見えなくなり、議論の流れが途切れる。見せ方は画面の側で決めるほうが直しやすい
- **要約から本文を作らない理由**: 本文には `[引用: …]` の形や用語が混ざるので、そのまま要約の代わりにすると非エンジニアに伝わらない（#139）

## 原価

実測は後回しにした（2026-09-30 オーナー）。ADR-085 で約束した入力・出力トークンの実測は、LIVE-4（#198）の最初の実機確認のときに、今回の増分とまとめて行う。

日本語1文字＝1トークンとして多めに見積もると、1解析あたりの増分は次のとおり。単価は gemini-2.5-flash が入力 $0.30・出力 $2.50、gemini-2.5-pro が入力 $1.25・出力 $10（いずれも100万トークンあたり、公開価格。実測のときに請求額と突き合わせる）。150円/ドルで換算した。

| 対象 | 増える量 | 1解析あたり |
|---|---|---|
| 3人の出力（要約・根拠・項目名） | 1回 約330 × 6回 ≒ 2,000 | 約¥0.75 |
| 3人の入力（画面用の書き方の指示） | 1回 約650 × 6回 ≒ 3,900 | 約¥0.18 |
| ディレクターの出力（まとめの一言） | 約150 | 約¥0.23 |
| ディレクターの入力（書き方の指示） | 約200 | 約¥0.04 |
| 合計 | | 約¥1.2 |

Pro の1解析の原価（ADR-039 の SerpAPI ¥16.5）に比べると約7%で、LIVE-1 の増分（約2%）より大きい。実測で見積もりより大きければ、要約の上限や根拠の項目を見直す。

## 申し送り

- LIVE-3（#197）: `DebateUtterance` を1件ずつ保存する。いまは `runShortDebate` が最後にまとめて返すので、各発言の直後に保存を差し込む形（関数を受け取るなど）に変える。ディレクターの1件は、`generateSingleShot` のあとに保存する
- LIVE-5（#199）: 要約が空の発言の見せ方を決める。立場の表示名は `DebateStance`、根拠の見出しは `DebateEvidenceKind` の中身に合わせる（例: 「根拠：測定結果（質問ごとの言及）」「根拠：改善タスク 2」）
- LIVE-4（#198）: 最初の実機確認で、入力・出力トークンを実測する（ADR-085 と今回の分）
