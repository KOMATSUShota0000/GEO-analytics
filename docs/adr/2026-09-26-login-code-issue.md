# ADR-072: ログインコードを発行し、登録の有無を外から見分けられない形で送る

## 日付
2026-09-26

## 状況

ログインを「メールに届く6桁のコード」に切り替える（#144）。その前半として、登録済みのメールアドレス宛てにコードを発行して送る API を作る（#146）。照合は AUTH-2b（#151）、送信回数の上限は AUTH-3（#147）、画面は AUTH-4（#148）で行う。

オーナー確定事項（#144）のうち、本件に関わるもの:

- コードは6桁の数字、10分で期限切れ（確定事項4）
- 登録されていないアドレスでも応答は同じにし、メールは送らない（確定事項3）
- メールの件名にコードを入れない（確定事項13）
- 自動テストでもメールは Mailpit で受け取る（確定事項15）
- 入力されたメールアドレスの大文字・小文字は区別しない（2026-09-26）
- メールの文面（2026-09-26）

## 決定

**`POST /api/auth/code` を追加する。ユーザーの検索は登録の有無にかかわらず同じく行い、登録済みのときだけ、コードの保存と送信を別スレッドで行ってすぐ 202 を返す。**

| | 内容 |
|---|---|
| 保存先 | 新しい表 `login_codes`（V143）。**ユーザーごとに1行**（`user_id` が主キー）で、新しいコードは同じ行を上書きする |
| コードの持ち方 | 保存するのは HMAC-SHA256（16進64文字）だけ。鍵は JWT の署名鍵から用途名で派生させる |
| 応答 | 常に `202 Accepted`（本文なし）。形式の誤りだけ `400` |
| 送信 | 仮想スレッド（`login-code-org-{組織}-user-{ユーザー}`）で送る。SMTP への同時接続は4本まで |
| メール | 件名「GEOアナリティクスのログインコード」、差出人名「GEOアナリティクス」、テキストのみ。本文にコード・有効期限の時刻（日本時間）・他人に教えない注意 |
| アドレスの照合 | 前後の空白を落とし、大文字・小文字を区別しない |
| テナント隔離 | `login_codes` に `organization_id` と RLS を付けた。バッチ用ロール（RLS を素通りする）からは権限を外した |

## 理由

### 登録の有無を外から見分けられないようにする

応答の内容・ステータスを同じにするだけでは足りず、**応答時間**でも見分けられてしまう。メールの送信（SMTP）は数百ミリ秒かかるので、送信を待ってから応答すると、登録済みのときだけ遅くなる。

そこで、登録の有無で差が出ない「ユーザーの検索」だけをリクエストのスレッドで行い、保存と送信は別スレッドに回してすぐ戻る。登録済みのときだけ増えるのはスレッドの起動（マイクロ秒単位）だけになる。

### ユーザーごとに1行にする

「古いコードを無効にしてから新しいコードを入れる」を2文で書くと、同時に2回要求されたときに有効なコードが2つできる。`user_id` を主キーにし、`INSERT ... ON CONFLICT (user_id) DO UPDATE` の1文で上書きすれば、古いコードは必ず消え、失敗回数と使用済みの印も戻る。コードは10分で使えなくなるので、履歴を残す必要は無い。

### ハッシュに HMAC を使う

6桁のコードは100万通りしかない。素の SHA-256 で保存すると、データベースが漏れたときに一瞬で逆算される。サーバーだけが持つ鍵で HMAC を取れば、データベースだけでは逆算できない。ユーザーIDも混ぜ、同じコードでもユーザーごとに別のハッシュになるようにした。

鍵には新しい環境変数を増やさず、JWT の署名鍵から用途名（`geo-analytics/login-code/v1`）で派生させた鍵を使う。署名鍵をそのまま使い回すと鍵の用途が混ざるため。署名鍵を変えると有効中のコードは使えなくなるが、有効期限は10分なので実害は小さい。

パスワード用の BCrypt（`PasswordEncoder`）は使わなかった。パスワードでのログインごと AUTH-5（#149）で撤去するため。

### 保存はサービス層のトランザクションで行う

RLS の組織IDは、`RlsConnectionInterceptor` が `@Transactional` の呼び出しを捉えて接続へ渡す。ところが、リポジトリのメソッドに `@Transactional` を付けて単体で呼ぶと、トランザクションが始まる前に検査され、「トランザクションなしのアクセス」として遮断された。また、Spring Data が用意する `findById` などは、リポジトリを直接呼ぶとこの仕組みを通らず、組織IDが渡らない。

そこで、読み書きはサービス（`LoginCodeStore`）の `@Transactional` メソッドを通す。AUTH-2b の照合もここに足す。結合テストでリポジトリを直接読むときは、組織IDの設定をトランザクション内で明示的に行っている。

### 大文字・小文字を区別しない

スマホで先頭が大文字になったり、名刺どおり大文字を交ぜて入力したりしても届くようにする（オーナー確定）。表の一意制約は大文字・小文字を区別するので、大文字違いの行が複数あり得る。その場合は登録の早い方に決め打ちする。

## 結果

- 未登録のアドレスは、ログに「登録されていないアドレスへの要求」とだけ残す（アドレスは残さない）。
- 送信に失敗しても応答は変わらない（202）。失敗はログにだけ残る。利用者には「届かない場合は再送」と案内する（AUTH-4）。
- **送信回数の上限はまだ無い。** 全体のレート制限はワークスペース単位で、ログイン前は必ず 429 になるため、この経路は対象外にした。専用の上限は AUTH-3（#147）で入れる。画面からはまだ呼ばれない（AUTH-4）。
- 期限切れや使用済みの行は、次にコードを発行したときに上書きされる。定期的な掃除は入れていない（1ユーザー1行なので増え続けない）。
- ログイン前の経路として `/api/auth/code` を、認可の許可リスト・CSRF の除外・テナントヘッダーの除外・全体のレート制限の除外の4か所に足した（今の `/api/login` と同じ扱い）。
