# ADR-079: 解析完了のお知らせをメールだけにし、宛先を3件まで持てるようにする

## 日付
2026-09-28

## 状況

解析が終わると、プロジェクトの設定に登録した Slack（Incoming Webhook URL）とメール（1件）へお知らせを送る仕組みがあった（`NotificationService`）。調べると次の問題があった（#173, #174）。

- **お知らせが一度も送られていなかった。** `NotificationService.deliver` はプロジェクト・解析結果・前回のジョブをリポジトリから直接読んでいた。`RlsConnectionInterceptor` はサービスの `@Transactional` の呼び出しでしか RLS 用の組織IDを接続へ渡さない（ADR `2026-09-26-login-code-issue.md`）。そのため `api_worker` の接続ではプロジェクトが見えず、何もせずに終わっていた
- **設定画面の読み込みが毎回失敗していた。** `ProjectSettingsService.getSettings` も同じ理由で 404 を返していた。本文が空だったので画面にエラーが出ず、保存した値も表示されなかった。保存（`patch`）は `@Transactional` なので動いていた
- **Slack 通知の設定が利用者に難しかった。** Incoming Webhook URL を得るには、Slack の開発者向けサイトでアプリを作って発行する必要がある。代理店のディレクターや営業には向かない
- **宛先が1件だけだった。** 担当者のメールと Slack の両方で受け取れない
- 保存に失敗したとき、画面はサーバーの `message` ではなく `detail` を読んでいたため、英語の JSON がそのまま出ていた
- お知らせの本文で、質問ごとの SoM と差が丸められずに出ていた（削除した Slack 版は小数1桁に丸めていた）

## 決定

- **Slack 通知をやめ、メールだけにする**（オーナー確定）。Slack で受け取りたい人には、Slack のチャンネル用メールアドレス（有料プラン）を宛先に入れてもらい、画面で案内する
- **宛先は3件まで**（オーナー確定）。担当者・上司や営業・Slack のチャンネル用アドレスで足りる。それ以上の人数へは共有アドレスで届ける
- **宛先は `projects.notification_emails`（`text[]`）に持つ**（オーナー確定）。`CHECK (cardinality(notification_emails) <= 3)` を掛ける。`slack_webhook_url` と `notification_email` は削除し、既存の `notification_email` は前後の空白を除いて引き継ぐ（V145）。本番の利用者はまだいないため、移行の案内は要らない
- お知らせの読み出しを `ProjectAuditNoticeReader.read`（`@Transactional(readOnly = true)`）へ分ける。`NotificationService.deliver` は、ワークスペースを束縛してからこれを呼び、メールの送信はトランザクションの外で行う
- `ProjectSettingsService.getSettings` に `@Transactional(readOnly = true)` を付ける
- 宛先ごとに1通ずつ送り、1件の失敗でほかの宛先を止めない
- 宛先は保存時に、前後の空白を除き、空を捨て、大文字・小文字だけが違うものを1件にまとめ（最初の書き方を残す）、形式と長さ（320文字まで）を確かめてから件数を数える
- 画面は、読み込みに成功するまで入力欄を出さない。失敗したまま保存すると、空の宛先で上書きしてしまうため
- お知らせの本文の値は小数1桁にそろえる。並べ替えは丸める前の差で行う

## 理由

### 別テーブルではなく配列の列にする

宛先は3件までの短い並びで、宛先ごとの属性（配信停止の印など）も持たない。別テーブル（1行＝1件。正規化の原則どおりの形）にすると、RLS のポリシー・エンティティ・リポジトリが増え、今回見つかった「組織IDが渡らない」落とし穴に気をつける箇所も増える。オーナーと比べたうえで、配列の列を選んだ。宛先ごとの属性が要るようになったら、別テーブルへ移す。

### エンティティでは `String[]` で持つ

`List<String>` に `@JdbcTypeCode(SqlTypes.ARRAY)` を付けると、Hibernate 6.6 のスキーマ検証が列の型を JSON として期待し、`_text (Types#ARRAY)` と食い違って起動できなかった。配列で持ち、getter・setter で `List` に変換する。

### 読み出しを別のクラスへ分ける

RLS の組織IDを渡すには、Spring のプロキシを通る `@Transactional` の呼び出しが要る。同じクラスの中から呼んでもプロキシを通らないため、ログインコード（`LoginCodeStore`）と同じく別のクラスに分けた。メール送信（SMTP）の待ち時間の間 DB のトランザクションを握らないよう、読み出しだけをトランザクションに入れる。

### 宛先ごとに1通ずつ送る

1通に宛先を並べると、受け取った人同士にアドレスが見える。また、1件のアドレスの不備で、ほかの宛先にも届かなくなる。

### エラー文にアドレスを含めない

`GlobalExceptionHandler` は `IllegalArgumentException` をメッセージごとログに出す。入力されたアドレスがログに残らないよう、エラー文には含めない。

## 結果

- 解析が終わると、登録した宛先（3件まで）に1通ずつお知らせが届く。RLS が効く接続と Mailpit を使う結合テスト（`ProjectNotificationIntegrationTest`）で確かめた
- 設定画面で保存した宛先が表示されるようになった
- 画面の実機確認はマージ後にオーナーが行う（開発用 DB を共有しているため、マージ前にこのブランチを動かすと、起動中のアプリの DB に V145 が当たってしまう）
- 残課題
  - Pro 以上の解析では「解析完了」の合図が2回出るため、お知らせも2通届く疑いがある（#176）
  - 同じ合図を受ける資産スナップショットの保存も、同じ原因で動いていない疑いがある（#180）
  - 定期監査はまだ動かない（#177）。画面のトグルは、作り直すまで今のまま残す
