# ADR-039: GEO 測定対象の是正（自社サイト本文から実測 AI Overview へ）

## 日付
2026-09-10

## 状況

本プロダクトは「生成AIの回答内でブランドがどう扱われているか」を測ると称してきた。実データによる検証（#51 / #71）で、**実際には自社サイトの本文を解析していた**ことが判明した。

リアルタイム経路（`JobQuerySubmissionService:300`）は `target_url` があれば自社サイトをクロールし、その本文をプロンプトへ渡す。ところがプロンプトは渡されるテキストをこう説明している。

```
"Based on the provided extracted text from an AI-generated answer, ..."
```

LLM はこれを「AI 回答」と解釈し、`response` に自社サイトの本文をほぼそのまま書き戻していた。

```
実測: クエリ「クラウド会計ソフト おすすめ」に対する response[:120]
  = 無料ではじめる ログイン 個人事業主向け 製品をお選びください freee会計 …
    （freee のトップページのナビゲーション）
```

全プランの既定クエリ数（STANDARD=3 / PRO=10 / EXPERT=30）は `realtimeBatchMax`（10 / 50 / 50）以下であり、**通常のジョブはすべてこの経路に流れる**。

### 症状

SoM が算術的に 12.0 へ固定される。

```
sourceWeight 0.3（自社ドメインは PRTIMES/知恵袋以外なので必ず LOW）→ normalized 0.2
mentionSignal 常に飽和 1.0
citationBonus 常に 0（自社サイトに順位リストは存在しない）
pwimScore = 0.6×0.2 + 0.4×0 = 0.12 → 12.0%
```

実測3件（freee PRO / freee STANDARD / サイボウズ PRO）がすべて `11.999999999999998`。ブランドも業種も違うのに同値だった。

### 経路によって材料が違う

| 経路 | LLM へ渡す材料 | 使われる条件 |
|---|---|---|
| リアルタイム（`verifyWithUrl`） | クロールした自社サイト本文 | クエリ数 ≤ `realtimeBatchMax` |
| バッチ（`GeminiBatchPromptText`） | なし（`userTextBrandQueryOnly`） | クエリ数 > `realtimeBatchMax` |

同じジョブでもクエリ本数によって測定方法が変わるのに、同じ `calculation_version` で保存されていた。

### 本物の AI 回答は既に取得され、捨てられていた

`AsyncSgeMeasurementService` が全プラン・全クエリで SerpAPI を叩き、結果を `sge_results` に保存していた。**しかし本番コードから一度も読まれていない**（参照は統合テストのみ）。

## 決定

### 1. 測定の材料を「実測の Google AI Overview」とする

SerpAPI の AI Overview を測定対象とする。実測で、ユーザーが打つクエリのみで検索すれば**本文が1コールで返る**ことを確認した。

```
検索: 「クラウド会計ソフト おすすめ」
ai_overview.text_blocks[2] = list
  - freee freee会計                              ← 1番目
  - マネーフォワード マネーフォワード クラウド会計  ← 2番目
  - 弥生 弥生会計 Next                            ← 3番目
ai_overview.references = 6件（accounting.cast-er.com / leapal.jp / aspicjapan.org …）
```

言及・順位・競合・引用元のすべてが実データで揃う。LLM に想像させる必要がない。

### 2. 実測が取れないクエリは LLM 生成の回答で補完し、レポート上で区別する

AI Overview が表示されないクエリは存在する。その場合は LLM に回答を生成させて材料とし、**「実測」か「推定」かをレポートに必ず明示する**（`.cursorrules` 11節「不確実性の可視化」）。

### 3. スコアの物差しはプラン共通とし、上位プランで売るのは「実測という証拠」

プラン別にスコアの算出方法を変えない。上位プランには実測の証拠（AI Overview の本文・引用元）を追加で提示する。

### 4. AI Overview は全クエリで取得する

代表クエリのみに絞る案は却下。実測が1コールで済むことが判明し、原価が当初見積もりの半分になったため。

### 5. `sourceWeight` を SoM から撤去する

第三者性の評価は権威軸へ集約する。SoM には持たせない。

### 6. `calculation_version` は新しい版名を切る

`V13_GEO4AXIS` のまま中身を変えず、新しい版名で保存して旧データと区別する。

### 7. 測定クエリからブランド名を外す

`GeoCompetitorQueryBuilder.build(brandName, query)` による「ブランド名＋クエリ」での検索をやめ、ユーザーのクエリのみで検索する。

## 理由

### 材料に実測を選ぶ理由

本プロダクトは制作会社・代理店が**自分の顧客への提案に使う**もの。提案書に載るのが「実際に Google の AI 回答でこうなっています」か「AI に聞いたらこう答えると思われます」かで、説得力と単価が変わる。

そして**追加原価がゼロ**である。SerpAPI は既に全プラン・全クエリで叩かれており、結果が捨てられていただけ。使うのは「既に買ったものを使う」ことに等しい。

### 物差しをプラン共通にする理由

プラン別にスコアの算出方法を変えると、**同じ顧客の成長チャートに段差ができる**。サイトを何も変えていないのにアップグレードした瞬間スコアが動く。

- 下がった場合: 顧客は「金を払った直後にスコアが下がった」体験をする。解約リスク
- 上がった場合: 「課金した顧客に甘い数値を出すツール」に見え、レポート自体の信頼性が崩れる

どちらに転んでも損をする。物差しは共通にし、上位プランでは証拠が増える体験にする。

### `sourceWeight` を撤去する理由

権威軸の中核（`ThirdPartyMentionScorer`）とは測る軸が違う（広がり vs 質）ため、重複が理由ではない。撤去の理由は次の3点。

1. **第三者性を測っていない** — 渡しているのが解析対象＝自社サイトの URL であり、設計意図が実装で実行されていない
2. **判別能力がゼロ** — PRTIMES と知恵袋以外はすべて 0.3。自社サイト解析では常に定数
3. **天井を作っている** — `0.3/1.5 = 0.2` が乗るため、言及成分が 12点を超えられない

因果の位置も違う。**第三者からの信頼は「AI 回答に出やすくなる原因」であり、SoM は「AI 回答での見え方という結果」**。原因と結果を1つの数値へ混ぜると、スコアが動いたときにどちらが動いたのか読めなくなる。分けておけば「権威軸は伸びたのに SoM が伸びていない＝露出は増えたが回答内で目立てていない」という診断ができ、改善提案の精度が上がる。

### 測定クエリからブランド名を外す理由

検索語にブランド名を入れれば、AI 回答に自社が出るのは当たり前になる。**測定が自作自演になる。** 実測でも「freee クラウド会計ソフト おすすめ」で検索した場合は `page_token` のみが返り本文が取れず、クエリのみの場合は本文が直接返った。

## 原価

プラン料金: Standard ¥9,800 / Pro ¥29,800 / Expert ¥59,800（税抜・月額）。限界利益率86%死守により原価予算は売上の14%。

SerpAPI Production プラン（\$150/月・15,000検索 = \$0.010/検索、150円/ドル換算で ¥1.5/検索）。

| | クエリ数 | AI Overview | 権威軸 | 合計 | 解析1回 | 月あたり黒字上限 |
|---|---|---|---|---|---|---|
| Standard | 3 | 3 | 1 | 4 | ¥6 | 228解析 |
| Pro | 10 | 10 | 1 | 11 | ¥16.5 | 252解析 |
| Expert | 30 | 30 | 1 | 31 | ¥46.5 | 180解析 |

`page_token` が返るケースのみ2コール目が必要になる。

**申し送り**: 累計上限（10 / 500 / 2,000件）まで使い切られると Pro / Expert は SerpAPI だけで予算を超過する。料金体系か上限のいずれかは将来調整が要る（優先度低）。また Expert はクエリ数が Pro の3倍だが月額は約2倍で、解析1回の原価が Pro 比2.9倍と単位経済が薄い。

## 結果

本 ADR は決定の記録であり、実装は伴わない。実装は次の子 issue で行う。

| | 内容 |
|---|---|
| #71 | AI Overview の取得を修正し `sge_results` を読み出してスコアの材料にする |
| #58 | プロンプトに `response` 生成の明示指示を入れる |
| #66 | `ai_citation_position` を `text_blocks` から Java で算出する |
| #68 | `test-sync` を本番のリアルタイム経路と揃える |
| #70 | プロンプト構築を SSOT 化する（挙動不変。先に通すと上記の実装が1箇所で済む） |
| #60 | `sourceWeight` 撤去に伴うスコア絶対値の再調整を含む |

**検証指標**: SoM が 12.0 の定数から解放され、ブランドごとに異なる値を取ること。

**トレードオフ/申し送り**:

- AI Overview は Google に限られる。ChatGPT や Claude の回答内での可視性は測れない
- `references` は「競合企業」とは限らず比較記事やメディアも含む。競合サイトのルーブリック監査を復活させる際（#76）は選別ロジックが要る
- 本 ADR は ADR-034（`competitorResults` の温存を指示）の前提を更新する。`competitorComparison` は削除対象ではなく、材料が自社サイト本文だったために競合を返せていなかっただけである（#40 はこの結論を受けてクローズ済み）
