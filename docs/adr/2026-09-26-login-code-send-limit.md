# ADR-074: ログインコードの送信回数を、直近の送信時刻で正確に数えて上限をかける

## 日付
2026-09-26

## 状況

ログインコードの発行（ADR-072）には送信回数の上限が無かった。1つのコードで試せるのは5回（ADR-073）なので、送信回数の上限がそのまま「総当たりで試せる回数」の上限になる（#147）。大量に送らせられると、迷惑メール扱いで送信元の評判が落ち、メールが唯一の入口であるログインが成り立たなくなる。

オーナー確定事項（#144）:

| | 上限 |
|---|---|
| 同じアドレス | 再送は60秒あける・1時間5回・1日10回（確定事項5） |
| 同じ接続元（IPアドレス） | 1時間20回（確定事項5） |

- 回数はメモリ上で数える（確定事項10）
- 未登録のアドレスも同じように数える（確定事項12）
- 画面が「60秒待ち」と「回数の上限」で文言を変えられるようにする（#147）

## 決定

**アドレスごと・接続元ごとに直近の送信時刻をメモリ上に覚え、「どの1時間／どの24時間を切り取っても上限以下」になるように数える（`LoginCodeSendLimiter`）。上限に当たったら送らずに 429 を返す。**

| | 内容 |
|---|---|
| 判定の順 | ユーザーを探す**前**に判定する（登録の有無で差を出さない） |
| 429 の種類 | `login_code_resend_too_soon`（60秒待ち）／`login_code_send_limit`（回数の上限）。`details.retry_after_seconds` と `Retry-After` ヘッダーで待ち時間を返す |
| 両方に当たったとき | 回数の上限を優先し、待ち時間は長い方を返す |
| 断った要求 | 数えない |
| アドレスの扱い | 前後の空白を落とし、大文字・小文字を区別しない（発行・照合と同じ） |
| 設定値 | `app.auth.login-code.resend-interval` / `max-sends-per-address-per-hour` / `max-sends-per-address-per-day` / `max-sends-per-client-per-hour` |

## 理由

### Bucket4j ではなく直近の送信時刻で数える

#147 の起票時は既存の Bucket4j で数える想定だった。しかし Bucket4j の「枠が少しずつ回復する」方式では、「1時間5回」の枠が12分ごとに1回分ずつ回復する。60秒おきに送り続けると最初の1時間で最大10回、1日の枠も最初の24時間で最大20回ほど通り、決めごとどおりにならない。長い目で見た平均は同じだが、決めた数字と動きが食い違う。

直近の送信時刻を覚えて数えれば、どの1時間でも5回まで、どの24時間でも10回までになる。覚える時刻はアドレスごとに最大10個、接続元ごとに最大20個で、メモリ上で正確に数えられる（オーナー確定 2026-09-26）。

### 1つのロックでまとめて判定する

アドレスと接続元の2つの記録を別々に確かめて記録すると、同時の要求が両方とも「まだ上限前」と判断して上限を超えて通る。確かめてから記録するまでを1つのロック（`ReentrantLock`）の中で行う。送信の要求は低頻度なので、全体で1つのロックでも詰まらない。`synchronized` は仮想スレッドを固定するため使わない（`.cursorrules` 8節）。

### 覚える件数に上限を置く

架空のアドレスを大量に送られても覚える量が際限なく増えないよう、アドレス・接続元それぞれ10万件までにし、あふれた分は古いものから忘れる（Caffeine）。忘れたアドレスは数え直しになるが、接続元ごとの上限が別にかかるので総当たりは防げる。記録はアドレスが1日、接続元が1時間使われなければ消える。

### 種類を返しても登録の有無は分からない

上限は登録の有無に関係なく数えるので、「60秒待ち」と「回数の上限」の区別を返しても登録の有無は分からない。画面（AUTH-4）はこの区別で文言を変える。

## 結果

- 再起動すると数え直しになる（確定事項10）。サーバーを2台以上にするときは、Redis 等の共有の置き場へ移す。
- 接続元は `ClientIpResolver`（`request.getRemoteAddr()`）で取る。`server.forward-headers-strategy: native` と `internal-proxies` の設定により、内部のプロキシを経由した要求では `X-Forwarded-For` の申告が使われる。結合テストはこれを使ってテストごとに接続元を分けている。
- 照合（`/api/auth/code/verify`）には送信回数の上限をかけていない。照合で試せる回数は、1コード5回（ADR-073）と送信回数の上限の掛け算で決まる。
- 全体のレート制限（`RateLimitFilter`、ワークスペース単位）からは、ADR-072・073 で除外したまま。二重には数えない。
- 発行・照合の結合テストは、同じアドレスへ続けて発行するため、テストの設定で上限を外している。上限は `LoginCodeSendLimitIntegrationTest` で既定の数字のまま確かめる。
