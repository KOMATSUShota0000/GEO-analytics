# ADR-059: 4ペルソナ議論を解析経路へ配線し、全プランで走らせる

## 日付
2026-09-20

## 状況

CLAUDE.md がプロダクトの核の第一項に挙げる「4人のAIペルソナによる多角議論と改善ロードマップ自動生成」が、**解析レポートでは機能していなかった**（#73）。

調査で分かった実態:

| | 状態 |
|---|---|
| `DebateAdviceGeneratorService`（本物の4ペルソナ議論。ANALYST / SKEPTIC / INNOVATOR / DIRECTOR の専用モデル、チケット200消費） | **実装済み** |
| `StrategyInsightService.rollupJobWithSource`（議論を呼び、失敗時はテンプレートへ縮退） | **実装済み** |
| `GapAnalysisService.runForJob`（議論を呼んで結果をジョブへ永続化） | **実装済み** |
| これを呼ぶ経路 | **バッチ経路（`GeminiResultProcessor`）のみ** |

つまり**リアルタイム経路の解析では議論が一度も走っていなかった**。さらに議論は PRO / EXPERT に限定されていた。

## 決定（オーナー確定 2026-09-20）

### 1. リアルタイム経路からも同じ入口を呼ぶ

解析完了後（ベンチマーク保存・ルーブリック監査・改善タスク生成のあと）に `GapAnalysisService.scheduleForJob(jobId)` を呼ぶ。バッチ経路と同じ入口を使い、**経路によって提案の作り方が変わる状態を作らない**。

### 2. 全プランで議論を走らせる

`generateForJob` のプラン条件（PRO / EXPERT）を外す。課金識別子が揃わない場合だけ、チケットを予約できないため単発生成へ落とす。

## 理由

### 表示のたびに走らせない

ジョブ全体アドバイスはレポート表示のたびに計算される作りだった。ここに議論を直接つなぐと、**画面を開くたびにチケット200を消費する**。既存の設計どおり「解析完了時に1回だけ生成して `jobs` へ永続化し、表示は保存値を読む」形に合わせる。

### 全プランで走らせる理由

プランで議論の有無を分けると、**改善提案の質がプランで別物**になる。CLAUDE.md の核は「WOW体験」であり、体験の根幹をプランで削らない（オーナー確定）。上位プランの価値は測定の本数と実測の証拠（ADR-039 の決定3）で出す。

### 失敗しても解析を落とさない

議論は LLM を4回以上呼ぶため失敗しうる。`StrategyInsightService` がテンプレートへ縮退し、`job_advice_source` に生成元（`AI_DEBATE` / `AI` / `TEMPLATE_FALLBACK`）が残る。チケットは失敗時に全額返金される（既存実装）。

## 結果

- リアルタイム経路の解析でも、4ペルソナ議論にもとづく改善提案が出る。
- 1解析あたりチケット200を追加で消費する（全プラン）。
- 議論の過程そのものの表示は行わない（#74 で将来対応）。
- ペルソナ名が2系統ある問題（解析側の `SEO_EXPERT` 等）は #78 で統一する。
