# ADR-095: 議論の発言を1件ずつ保存し、議論の状態をジョブに持たせる

## 日付

2026-09-30

## 状況

解析結果の画面の待ち時間に、4人のAIの議論を1発言ずつ見せる（#194）。LIVE-2（#196、ADR-094）で、各発言に画面用の要約・誰への返事か・根拠が付いた。次は、発言を保存して、画面が議論の途中でも読めるようにする（#197）。

- 議論の全文は保存されず、ディレクターの結論（総合診断・ロードマップ・少数意見）だけが `jobs` に残っていた
- 議論は、解析の完了のあと裏の仮想スレッドで走る（`GapAnalysisService.scheduleForJob`）。リアルタイムの経路は、議論を起こした直後に解析を完了にする
- 裏の処理の DB の読み書きは `BatchPersistenceService`（`batch_worker`、RLS を素通りする）を通る
- 議論を生成する `DebateAdviceGeneratorService` は DB を持たない
- 議論が走らないときがある: 質問が2本未満・指標が出ない・プロジェクトの前提が読めない・課金の識別子が揃わない

## 決定

### 1. 発言は新しいテーブル `job_debate_utterances` に1件ずつ保存する（V146）

| 列 | 中身 |
|---|---|
| `job_id` | ジョブ（削除されたら発言も消える） |
| `organization_id` | 組織。RLS に使う |
| `seq` | 話した順（1始まり。ジョブの中で重ならない） |
| `round` | ラウンド。まとめ役の一言は NULL |
| `speaker` | 発言者（`ANALYST` など） |
| `summary` | 画面用の要約 |
| `reply_to`・`stance` | 誰への返事か・立場 |
| `evidence_kind`・`evidence_task_number`・`evidence_detail` | 根拠 |

- 議論用の本文は持たない。長く専門用語も混ざり、画面には出さないため（ADR-094）
- RLS は `jobs` と同じく組織単位にした。`jobs` は行ごとに `workspaces` を引いて組織を求めているが、新しいテーブルは組織IDを列に持たせ、そのまま比べる
- 書くのは裏の処理（`batch_worker`）だけで、画面（`api_worker`）は読むだけにした。既定の権限（V3）で付く分を外してから、`api_worker` に SELECT、`batch_worker` に SELECT・INSERT・DELETE を付ける

### 2. 議論の状態は `jobs.debate_status` に持たせる（2026-09-30 オーナー確定）

| 値 | 意味 |
|---|---|
| `RUNNING` | 議論（または総合診断の作成）が終わっていない。発言が0件なら準備中 |
| `COMPLETED` | 議論が終わり、総合診断が議論をもとに作られた |
| `SKIPPED` | 議論をせずに総合診断を作った |
| `FAILED` | 議論が失敗し、チケットを返して議論なしで総合診断を作った |
| NULL | この列より前の解析。発言は保存されていない |

1ジョブに状態は1つだけなので、新しいテーブルではなく列にした。LIVE-4 の問い合わせはもともと `jobs` を読むので、読み出しも増えない。

### 3. 状態を書き込む順番

- **`RUNNING` は、裏の処理を起こす前に付ける**（`scheduleForJob` の中で同期的に）。リアルタイムの経路は直後に解析を完了にするので、画面が「完了」を受け取った時点で、議論がまだ終わっていないことを読める
- **終わりの印（`COMPLETED`・`SKIPPED`・`FAILED`）は、総合診断を書いたあとに付ける**。画面は印を見て問い合わせをやめるので、逆にすると総合診断の無いまま問い合わせが止まる
- 裏の処理が例外で落ちたら、`RUNNING` のときだけ `FAILED` にする（`abandonDebate`）。議論のあとで落ちたとき（外れ値の処理など）は、議論の結果は正しいので触らない

### 4. やり直し・失敗のときは、そのジョブの発言を消す（2026-09-30 オーナー確定）

- **やり直し**: 議論を始めるとき（`beginDebate`）に、そのジョブの前の発言を消して置き換える。総合診断とロードマップも最後の議論で上書きされるので、古い発言を残すと画面の結論と食い違う。今のコードに、同じジョブで議論が2回走る道は見つかっていない。念のための決まり
- **失敗**: 途中までの発言を消し、状態を `FAILED` にする。失敗したときの総合診断は、途中の議論を読まずに作り直されるので、残すと画面の発言と結論が食い違う

オーナーには「残す」「回数で区別して残す」も示した。履歴を残すと、原因の調査や、AI の出力のばらつきを比べるのに使える。ただ、読み出しで毎回「最後の回だけ」に絞る必要があり、得るものは小さいとして「消す」になった。

### 5. 保存は呼び出し元に任せる（`DebateRecorder`）

`DebateAdviceGeneratorService` は DB を持たないまま、発言を受け取る口 `DebateRecorder` を引数でもらう。

- 3人の発言は、次の発言者を呼ぶ前に `spoke` で渡す。画面が議論の途中でも読めるようにするため
- まとめ役の一言は、ディレクターの結論ができたあとに渡す
- 議論が失敗したら `failed` を呼ぶ
- `GapAnalysisService` の実装（`JobDebateRecorder`）が、番号を振って保存し、終わりの状態を決める（失敗の知らせがあれば `FAILED`、発言が1件以上あれば `COMPLETED`、無ければ `SKIPPED`）
- 保存に失敗しても、議論と総合診断は止めない（ログだけ残す）。画面に出る発言が欠けるだけで、解析は成立する

`generateForJob` には、受け手を渡さない従来の形（発言を保存しない呼び出し）も残した。

## 失敗の頻度（判断の材料）

開発用 DB では、議論が入った 2026-09-21 以降の7回がすべて確定し、返金（失敗）は0回だった。AI の1回の呼び出しは、エラーでもライブラリ（LangChain4j 0.36.2 の既定）が最大3回まで試す。失敗になるのは、Gemini の障害などで3回ともだめなときと、ディレクターの応答が読めない形だったときくらい。

## 申し送り

- LIVE-4（#198）: 問い合わせの返事に `debate_status` と発言の一覧を載せ、`RUNNING` のあいだは問い合わせを続ける。サーバーが議論の途中で止まる（再起動など）と `RUNNING` のまま残るので、時間の上限（`jobs.updated_at` からの経過など）を決める。画面側の読み出しは、`@Transactional` のサービスを別のクラスから呼んで行う（R-02）
- LIVE-6（#200）: `SKIPPED`・`FAILED`・NULL（古い解析）の表示を決める
- 失敗が本番で目立つようなら、「途中までの議論をディレクターに渡して結論を作る」を別の issue で考える（2026-09-30 オーナーと合意）。チケットを返すか取るかも、そのときに決める
