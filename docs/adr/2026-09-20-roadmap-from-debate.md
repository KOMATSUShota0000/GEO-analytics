# ADR-063: 改善ロードマップを4ペルソナ議論の成果物として出す

## 日付
2026-09-20

## 状況

CLAUDE.md がプロダクトの核の第一項に掲げる「多角議論と**改善ロードマップ自動生成**」のうち、ロードマップが未実装だった（#77）。

旧実装は、可視性検証（GBVS）の1コールに `roadmap_items` を**任意フィールドとして相乗り**させる形だった。実測8件すべてで省略され、消費コードも UI も存在しなかった。旧残骸は #60 / #68 の整理で既に撤去済みで、本 ADR は新規実装にあたる。

改善タスク（ADR-061）との違いは明確で、重複ではない。

| | 内容 | 形 |
|---|---|---|
| 改善タスク | **何を**やるか（優先度付き） | `rank` / `title` / `rationale` / `evidence` |
| 改善ロードマップ | **どの順番で・どのフェーズで**やるか | `phase` / `title` / `rationale` / `expected_impact` |

## 決定（オーナー確定 2026-09-19 / #77）

| 論点 | 決定 |
|---|---|
| 生成経路 | 4ペルソナ議論の DIRECTOR がロードマップまで構造化する |
| 追加の LLM 呼び出し | 立てない。既存の議論コールの成果物として出す（原価は増えない） |
| フェーズの粒度 | 「今すぐ／1〜3ヶ月／3〜6ヶ月」の3段 |

### フェーズは自由記述にせず列挙に固定する

`RoadmapPhase`（`NOW` / `SHORT_TERM` / `MID_TERM`）を作り、構造化出力スキーマでも `enum` として指定する。自由記述だと「短期」「中期」「すぐ」等が混在し、**並べ替えが壊れる**。表示名（「今すぐ」等）は enum が持ち、API が `phase_label` として返す。画面・PDF に日本語を散らすと表記ゆれの温床になるため。

### 保存時に順序を確定させる

LLM が返す順序は保証されない。`toRoadmapItems` でフェーズ順にソートしてから `jobs.roadmap_items`（V141, JSONB, `DEFAULT '[]'`）へ保存する。画面ごとに並べ替えると API・PDF・画面で並びがずれうるため、**保存時に一度だけ確定**させる（API 側にも保険のソートを置く）。

### 上限

最大6件（3フェーズ×2件）。`title` 60文字、`rationale` / `expected_impact` 各120文字。多すぎると「順番の提案」ではなく改善タスク一覧の再掲になり、2つの成果物の役割が溶ける。

### テンプレ経路では列を上書きしない

ADR-062 と同じく、議論が成立した回（`AdviceSource.AI`）だけが書き込む。テンプレフォールバックの回は `COALESCE(?::jsonb, roadmap_items)` で既存値を保つ。

## 影響

- 新規マイグレーション `V141__jobs_roadmap_items.sql`
- DIRECTOR の構造化出力スキーマ `DebateAdviceOutputSchema` に `roadmap_items` を必須で追加（ADR-062 で解析専用スキーマへ分離済みのため、オンボーディング側には影響しない）
- `JobAnalysisDetailResponse.roadmap_items` が増える（追加のみ）
- 画面と PDF に `RoadmapTimeline`（フェーズを横に並べ、前段の上に次段が積み上がることを示す）
