# ADR-046: バッチ経路でも実測 AI Overview を材料にする

## 日付
2026-09-19

## 状況

#92（ADR-045）でリアルタイム経路の材料を実測の AI Overview へ切り替えたが、バッチ経路（クエリ数が `realtimeBatchMax` を超えたときに走る Gemini Batch API 経路）は材料がサイト本文のままで、行は正直に `ESTIMATED` として記録していた。

バッチ経路は「全クエリをまとめて投入し、後から回収する」形のため、リアルタイム経路の「クエリごとに取得 → そのクエリの検証」をそのまま適用できない。

さらに、取得したはずの AI Overview 本文は `sge_results` に**生JSONとしてしか残っておらず**、本文を使いたい側が毎回 JSON を解釈し直す必要があった。

## 決定

### 1. バッチ投入の直前に、全クエリの AI Overview 取得を完了させる

`GeminiBatchExecutorService` が、未処理クエリの AI Overview を**同期で**取得・保存してから JSONL を組み立てる。バッチ経路はもともと非同期で遅いため、取得完了を待つコストは相対的に小さい。

### 2. ジョブ登録時の非同期取得は撤去する

投入直前に取得するなら、ジョブ登録時にも取得すると SerpAPI を二重に叩く。リアルタイム経路で外したのと同じ理由（ADR-045 の決定1）。

### 3. AI Overview 本文を `sge_results` に列として持つ

生JSONからの再抽出をやめ、`overview_body` 列に本文を保存する。プロンプト組み立て（投入時）と材料の記録（回収時）が別のタイミングで走るため、両者が同じ一次情報を読めるようにする。

### 4. 材料の別と版名はリアルタイム経路と同じ規則にする

本文が取れたクエリは `MEASURED`、取れなかったクエリは `ESTIMATED`。版名は両方とも `V14_AIOVERVIEW`。

## 理由

### 投入直前に取得する理由

バッチ投入は一度きりで、投入後にプロンプトを差し替えられない。取得が間に合わなければそのクエリは推定になるため、**取得の完了を待ってから投入する**のが唯一の確実な順序になる。

### 本文を列に持つ理由

回収は投入から数分〜数十分後に別のスレッドで走る。そのとき「このクエリは実測だったか」を判断する材料が必要になる。生JSONを再解釈すると、SerpAPI の応答形式が変わったときに投入時と回収時で判断が食い違う。

## 結果

- バッチ経路でも SoM が AI 回答の内容で動く。**値は変わる。**
- SerpAPI の呼び出し回数は変わらない（従来もジョブ登録時に全クエリ分叩いていた）。
- リアルタイムとバッチで材料の組み立てが `ConsultantPrompts.userBody` の1箇所に揃う（#70 で解消した「経路によって材料が違う」状態を再発させない）。
