# ADR-045: 検証の材料を実測の AI Overview へ切り替える

## 日付
2026-09-19

## 状況

「AI 回答の中でどれだけ見えているか」を測ると称しながら、**クロールした自社サイトの本文を材料にしていた**（ADR-039）。自社サイトに自社名が並ぶのは当然で、SoM は算術的に 12.0 へ固定されていた。

本物の AI Overview は既に SerpAPI から取得して `sge_results` へ保存していたが、**検証には渡していなかった**。しかも取得はジョブ全体を `@Async` で走らせており、実データでは10クエリ中9クエリが**取得完了前に検証済み**だった。

## 決定

### 1. クエリごとに「AI Overview 取得 → そのクエリの検証」と直列にする

リアルタイム経路では、クエリ単位で SerpAPI を叩き、その本文をそのクエリの検証材料に渡す。クエリ間は従来どおり並列のため、解析全体の待ち時間は最も遅いクエリ1本分で決まる。

**ジョブ全体の非同期取得はリアルタイム経路から外す。** 両方呼ぶと SerpAPI を二重に叩き、原価が倍になる。

### 2. 材料の優先順位を1箇所に閉じる

`ConsultantPrompts.userBody` が **実測 AI Overview > サイト本文 > 材料なし（推定）** の順で材料を選ぶ。実測が取れたクエリにはサイト本文を渡さない。

AI Overview 用のテンプレートは見出しで「AI-generated answer (Google AI Overview) follows」と明示する。ADR-044 の Step 1 が「ユーザー本文に AI-generated answer のブロックがあれば response へそのまま写す」と定めており、明示しないと写しの分岐が効かないため。

### 3. 材料の別を行ごとに記録する

`audit_histories.material_source`（`MEASURED` / `ESTIMATED`）を追加する。既定値は `ESTIMATED` とし、既存行とまだ切り替えていないバッチ経路の行は正直に推定として扱う（切り替えは #94）。

### 4. 版名を分ける

材料が AI Overview（またはその推定）の行は `V14_AIOVERVIEW`、サイト本文を材料にしている旧経路（test-sync。#68 で解消）は `V13_GEO4AXIS` のままとする。同じ式でも材料が変われば別の測定になるため。

## 理由

### クロールを検証経路から外す理由

材料を AI Overview にすると、クロール本文は検証プロンプトに渡らない。渡らないものを毎クエリ取りに行くのは無駄で、実際に同じ URL を10回クロールしていた。自社サイトの評価（ルーブリック監査・基礎スコア）は別経路が担っており、そちらは従来どおりクロールする。

`url` 自体は引き続き検証リクエストへ渡す。ドメイン由来の重み（`sourceWeight`）が従来どおり効くようにするため。この重み自体の撤去は #60 で行う。

### 取得に失敗したクエリを落とさない理由

SerpAPI の失敗や AI Overview 不在は日常的に起きる。1クエリの失敗で解析全体を落とさず、そのクエリだけ推定へ降格させる。降格したことは `material_source` とログに残るため、後から「何件が実測だったか」を検証できる。

## 結果

- SoM が材料の内容で動くようになる。**値は変わる**（このための PR）。
- 1解析あたりの SerpAPI 呼び出し回数は変わらない（従来もジョブ全体で全クエリ分叩いていた）。クロールは「クエリ数 × 1回」から 0 回になる。
- レポートでの実測／推定の区別は #93、バッチ経路の切り替えは #94。
- **本番から呼ばれなくなったもの**: `SyncVerificationService.verifyWithUrl`（クロール本文を材料にする検証）と `AsyncSgeMeasurementService.measureSgeForJob(job, queries)` の2引数版。後者は本 PR で撤去した。前者は test-sync を本番と揃える #68 で、そちらの経路ごと撤去する。
