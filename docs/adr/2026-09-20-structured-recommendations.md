# ADR-061: 改善タスクに根拠を持たせる

## 日付
2026-09-20

## 状況

「改善点を根拠付きで表示する」という要件に対し、**根拠を置く場所が型に無かった**（#79）。

```java
public record RemediationTask(
        UUID id, TaskCategory category, TaskPriority priority,
        String title, String content, double impactScore) {}   // ← 根拠のフィールドが無い
```

本文（`content`）の中に理由を混ぜて書かせることはできるが、**構造として取り出せない**ため、画面で「なぜ効くか」「どこが根拠か」を分けて見せられない。プロンプトも「証拠の範囲内で提案せよ」と言うだけで、根拠の**出力**は求めていなかった。

既存型の棚卸しでは、`evidence` を持つのはマイノリティ・レポートだけだった（そしてそれは解析側で使われていない → #80）。

## 決定（オーナー確定 2026-09-10「構造化は必須」）

`RemediationTask` に2つのフィールドを足す。

| フィールド | 意味 |
|---|---|
| `rationale` | **なぜ効くか**。GEO 露出・LLM 引用への作用を1〜2文で |
| `evidence` | **どこが根拠か**。与えられたルーブリック所見のどこに基づくかを引用で示す |

構造化出力スキーマで両方を必須にし、プロンプトでも「evidence に入力に無い内容を書いてはならない」と明示する（`.cursorrules` の Cite Before You Speak）。

## 理由

### 2つに分ける理由

「なぜ効くか」は提案の論理、「どこが根拠か」は入力への参照で、性質が違う。1つにまとめると、**根拠が無いまま論理だけを書く**ことを許してしまう。分けておけば、`evidence` が空のタスクを後から機械的に検出できる。

### 古いデータでは null を許す

`audit_histories.job_recommended_actions` に JSON で保存済みのタスクにはこの2項目が無い。必須にすると既存データの読み出しが壊れるため、**ドメイン型では null を許容し、画面では値があるときだけ表示する**。

### 文体の再生成で根拠を保持する

`TaskRegenerationService` は本文だけを作り直す。根拠は元の判断材料なので引き継ぐ。

## 結果

- 画面（タスクカード）に「なぜ効くか」「根拠」を分けて表示する。
- 新規に生成されるタスクは両方を必ず持つ（スキーマで必須）。
- 古いタスクは従来どおり本文のみ表示される。
