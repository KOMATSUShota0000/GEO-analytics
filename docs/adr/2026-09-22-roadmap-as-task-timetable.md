# ADR-070: 改善ロードマップを改善タスクの時間割にし、推奨アクションを外す

## 日付
2026-09-22

## 状況

解析結果画面に「やることリスト」が3つあり、どれをやればよいかわからなかった（#141）。

| 画面の場所 | 作り手 | AIに渡していた材料 |
|---|---|---|
| 水色の枠「ジョブ全体の戦略診断」の箇条書き3件（推奨アクション） | 4ペルソナ議論（DIRECTOR） | 業種・ターゲット・強み・クエリ数・スコアの中央値 |
| 改善ロードマップ（ADR-063） | 同上 | 同上 |
| 改善タスク（ADR-069） | `AiRemediationService` | 診断10項目のうち自社に無く競合にあるものと、その該当箇所 |

改善タスクは議論より先に生成・保存されている（`JobQuerySubmissionService` の呼び出し順）。しかし議論には渡しておらず、議論はサイトの中身を知らないまま一般論のロードマップを出していた。実例として、同じ会社のトップページと採用ページを解析した2件で、ロードマップの「今すぐ」が一字一句同じ「既存コンテンツへの構造化データ（Schema.org）実装」だった。改善タスクには構造化データの話が1件も無く、2つのリストで「今すぐやること」が食い違っていた。ロードマップの文章には「改Z'」「Visibility Stage」「Brand Recommendation」などの内部用語も出ていた。

調べる中で、画面の水色の枠の診断文が4ペルソナ議論の結果ではないこともわかった。状態確認API（`GET /api/v1/jobs/{jobId}`）が毎回テンプレートから作り直した文を返し、画面はそちらを優先表示していた。PDFレポートは保存済みの議論の診断文を出すため、画面とPDFで診断文が違っていた。

## 決定

**やることは改善タスクに一本化する。改善ロードマップは改善タスクの時間割にし、推奨アクションは外す。**（オーナー確定 2026-09-22）

| 役割 | 担当 |
|---|---|
| 現状とその理由 | 総合診断（旧「ジョブ全体の戦略診断」。診断文だけ） |
| いつ、何番まで終えるか | 改善ロードマップ |
| 具体的に何をするか | 改善タスク |

- 議論（4人と DIRECTOR）の入力に、改善タスクを取り組む順の番号付きで加えた。渡すのは「効果 大・すぐ直せる」のようなラベルとタイトルだけにした。
- DIRECTOR の構造化出力から `recommended_actions` を外し、`roadmap_items` に `last_task_number`（そのフェーズで最後に終えるタスク番号）を加えた。
- 保存する `RoadmapItem` には `firstTaskNumber` / `lastTaskNumber` を持たせ、画面ではフェーズごとに「改善タスク 1〜2」と出す。
- 改善タスクの並び順（効果の大きい順、同じ効果の中はすぐ直せる順）は、画面から外して `RemediationTaskOrder` に置いた。サーバーは保存時と返却時にこの順へ並べる。
- DIRECTOR に、改善タスクと同じ書き方のルールを加えた。読み手は非エンジニアを含むこと、平易な日本語で書くこと、入力の指標名や英語の用語を書かないことを指示している。
- 状態確認APIの診断文は、保存済みの総合診断を優先するように直した。テンプレートで埋めるのは保存前（解析中）だけになる。
- 水色の枠の見出しを「総合診断」に変えた。「ジョブ」は内部用語で、オーナーにも何の枠か伝わらなかった。

## 理由

### 番号の範囲で時間割を組ませる

ロードマップが改善タスクと別の施策名を並べる限り、2つのリストの食い違いは原理的に消えない。ロードマップには改善タスクの番号の範囲だけを持たせ、施策の中身は改善タスクに任せる。こうすると、2つが同じ中身を別の粒度で見せる関係になる。4ペルソナ議論（核①）の役割は、どこで区切るか、なぜその順か、終えると何が変わるかの判断として残る。LLM 呼び出しは増えない。

番号の範囲はサーバー側で補正する。改善タスクは番号順に進めるので、各フェーズは前のフェーズの続きから始まる連続した範囲でなければならない。AI が返す番号の重なり・抜け・逆順はフェーズ順に詰め、最後のフェーズを最後のタスクで閉じる。同じフェーズの2件目と、タスクを使い切ったあとのフェーズは落とす。AI の出力がどうであっても、時間割と改善タスクの番号が矛盾しないことを優先した。

### 並び順の単一情報源をサーバーに置く

ロードマップの番号は、議論の時点でサーバーが決めた並びを指す。画面が独自に並べ替えると、同じ「3番」が別のタスクを指しうる。並び順を `RemediationTaskOrder` だけに置き、画面は受け取った順に番号を振る。#141 より前に保存したタスクは取り組む順になっていないため、返却時にも並べ直す。

### 推奨アクションを作らせない

時間割になったロードマップと改善タスクがあれば、推奨アクションには役割が残らない。画面で隠すだけにすると、使われない出力のために毎回トークンを払い続けることになる。そのため DIRECTOR のスキーマからも外した。

## 結果

- 画面は、総合診断（現状）→ 改善ロードマップ（改善タスク何番をいつまでに）→ 改善タスク（番号順の作業）の構成になる。
- 改善タスクが無い解析（ギャップ無し・バッチ経路）では、ロードマップは番号無しの従来形で出る。スキーマは静的なので、その場合も `last_task_number` は必須で、0 を返させて捨てる。
- 印刷用のロードマップには番号を出さない。改善タスクがレポートに載っていないためで、載せるときに合わせて出す（#138）。
- `JobStatusResponse.recommended_actions` と `JobAnalysisDetailResponse.job_summary_recommended_actions` を API から外した。
- DB の `jobs.job_recommended_actions` 列は残した。議論失敗時のテンプレート経路は引き続き書き込むが、表示には使わない。列の削除は既存データを失うため、別途判断する。
- クエリごとの推奨アクション（検索クエリ一覧の「戦略診断・推奨」列）は今回の対象外で、そのまま残っている。
- ADR-063 の「改善タスクとロードマップは重複ではない（別の成果物）」は、「ロードマップは改善タスクの時間割」へ置き換わった。
