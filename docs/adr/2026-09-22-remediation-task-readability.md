# ADR-069: 改善タスクを非エンジニアにも読める文章にし、取り組む順に番号を付ける

## 日付
2026-09-22

## 状況

解析結果画面の「改善タスク（セクション別）」は、文章・ラベル・並び順のどれもが非エンジニアには読み取りにくく、何から手をつければよいかがわからなかった（#139）。開発DBに残っていた実データ2件（計20タスク）で、次の問題を確認した。

- **2つの物差しが区別なく並んでいた。** S/A/B級は効果の大きさ（AIが付けた impactScore が 0.7以上でS、0.4以上でA）で、`Impact 80%` のチップも同じ数値の言い換えだった。Spike（即効）/Slab（根本）はかかる時間の区別で、AIは課題1つにつき1件ずつペアで出す。入れ子の関係ではないのに1枚のカードに並んでいた。
- **並び順がかかる時間を無視していた。** S/A/B → impactScore だけで並べていたため、数時間で終わる作業と数か月かかる作業が交互に並んだ。
- **AIの文章が内部表現のままだった。** 根拠欄は20件すべて `criterionId=VERIFIABLE_AUTHORITY, self_status=NO` の形だった。本文の「なぜ必要か」と rationale（なぜ効くか）がほぼ同じ文で、1枚に2回出ていた。タイトルは「〜による権威性の担保」のように名詞を詰め込んだ形で、即効策の定義「Markdown 編集 1〜3 時間以内」から「Markdownで作成」が漏れていた。原因は、プロンプトに読み手と書き方の指示が無く、項目IDや判定値を英語のまま渡していたことにある。
- **画面の文言が事実と違っていた。** 「セクション別」はバックエンドが `targetSection` を返しておらず、全件が「サイト全体・未分類」の1グループに入っていた。ロック時の案内「基礎改修（Level 1）を完了させると解放」は、ADR-066 でプラン基準に変わる前の文だった。ロック時の本文「S級は実装の難度も高い」は、数時間で終わるS級タスクもあるので誤りだった。

## 決定

**効果の大きい順に並べ、同じ効果の中は「すぐ直せる対策」を先にして通し番号を振る。ラベルは区別の中身で呼び、AIには読み手と書き方を指示する。**

オーナーと対話して、次のとおり確定した（2026-09-22）。

| 項目 | 変更前 | 変更後 |
|---|---|---|
| 並び順 | S/A/B → impactScore | 効果 大 → 中 → 小。同じ効果の中は、すぐ直せる → 時間がかかる → impactScore の順。効果ごとのグループをまたいで通し番号 |
| かかる時間 | Spike（即効）／Slab（根本） | すぐ直せる／時間がかかる |
| 効果 | S 級・最優先／A 級／B 級 ＋ Impact % | 効果 大／中／小（Impact % は削除） |
| Pro未満で伏せるタスク | ― | 番号どおりの位置に置く |

生成側（`RemediationTaskPrompts`）は次のように変えた。

- 読み手（代理店の担当者と、その先のクライアント。エンジニアとは限らない）と、提案書にそのまま貼られることを明示した。
- 書き方のルールを加えた。平易な「です・ます」調で書く。「LLM」ではなく「AI」と書く。業界用語・内部用語は使わず、欠かせない専門用語にはかっこ書きで説明を添える。同じ内容を繰り返さない。
- title は「〜する」の形で30文字以内、content は手順だけ、evidence は「診断項目『〜』：自社は〜。競合は〜。」の文章にした。
- ギャップは項目IDではなく画面（`GeoScoreBreakdown`）と同じ日本語の項目名で渡し、状態も「記載なし／一部のみ記載あり」で渡す。

表示側では、効果ごとのグループ（大・中・小）に通し番号を付ける表示に変え、使われていなかった `targetSection` のセクション分けを撤去した。あわせて、ロック中も「なぜ効くか」を出すようにし、コピー時に改行を保つようにした。

## 理由

### 「何からやるか」を番号で答える

利用者が知りたいのは「どれから手をつけるか」で、そのためには効果とかかる時間の両方が要る。オーナーの判断は「効果 大をすべて終わらせてから効果 中へ。同じ効果の中では時間のかからないものから」である。効果の大きい対策を後回しにしないことを優先し、同じ効果なら早く成果が出るものを先にする。番号を効果ごとのグループをまたいだ通し番号にしたので、「上から順に進める」をそのまま指示として読める。

最初は「すぐ直せる対策をすべて先に、時間がかかる対策を後に」並べる案で実装した。しかしこの案では、効果 小のすぐ直せる対策が効果 大の時間がかかる対策より前に来る。オーナーの想定と違ったため、効果を先に見る順序へ改めた。

課題ごとに「すぐ直せる」と「時間がかかる」をペアで並べる案も検討した。課題と対策の対応は見えやすいが、1-1 の次に 1-2 と 2-1 のどちらをやるかは曖昧なまま残る。タスクがどの課題に属するかを保存する改修も要り、保存済みのデータはまとめられないため採らなかった。

### ラベルは区別の中身で呼ぶ

「Spike/Slab」は数理モデルの用語で、利用者には意味が通じない。「即効/根本」も、かかる時間の区別であることが伝わりにくかった（オーナーの指摘）。「S級」は効果の大きさを表しているのに、「最優先」と添えていたため、それだけで順番が決まるように見えていた。区別の中身をそのまま書けば、説明が無くても読める。

### 伏せるタスクも番号どおりに置く

プランによって番号が変わると、代理店とクライアントで同じタスクを別の番号で呼ぶことになる。上位に伏せたタスクが並ぶほど、Pro の価値も伝わる（核③ Teaser）。手順は伏せても、タイトルと「なぜ効くか」は見えるので、何をすればよいかの方向はわかる。

### AIの入力を日本語にする

AIは入力の見出しをそのまま出力へ写す。出力側で「IDを書くな」と指示するだけでなく、入力の段階で画面と同じ言葉にしておくと、根拠欄と画面の項目名もずれない。

## 結果

- 改善タスクは「効果 大」「効果 中」「効果 小」のグループに、通し番号付きで並ぶ。各カードには「すぐ直せる／時間がかかる」のラベルが付く。
- プロンプトの変更が効くのは次回の解析からで、保存済みのタスクの本文とタイトルは変わらない。根拠欄の `criterionId=...` 形式だけは、表示時に日本語の項目名へ置き換える（`humanizeEvidence`）。
- 内部の enum 名（`TaskCategory.SPIKE/SLAB`、`TaskPriority.S/A/B`）とプラン判定（`RemediationPriorityLevel`）は変えていない。
- 診断項目の日本語名は `frontend/src/lib/rubricLabels.ts` に移し、スコア内訳と改善タスクで共有する。バックエンドの `RemediationTaskPrompts#criterionLabel` も同じ名前を持つため、変えるときは両方を揃える。
